# 故障时间线对齐

## 故障起点怎么定

按优先级取，前面的可用就不用后面的：

1. 日志里第一条相关 ERROR 的时间戳
2. 指标（成功率、交易量）开始偏离基线的时间
3. 报表里写的「影响时间」区间起点
4. 告警时间

**告警时间排在最后。** 告警有聚合窗口和触发阈值，天然滞后于故障发生，常见滞后几分钟到十几分钟。
用告警时间当故障起点，会低估影响时长，也会错判事件顺序。

## 哪个系统是根因系统

以下三条都**不能**用来判断根因：

- 谁先告警。下游系统的业务指标往往比上游的技术指标更敏感，经常先响。
- 谁的告警级别高。级别反映业务影响大小，不反映因果方向。
- 谁的告警条数多。

正确的判断依据：

1. **谁的日志里有原始异常**。有完整异常堆栈、且异常来自自身组件的，是故障发生地；
   只是收不到响应、超时、成功率下降的，是受害者。
2. **调用链方向**。A 调 B，B 挂了导致 A 失败，根因在 B。看材料里的接口名、依赖描述、
   报表里的「关联系统影响分析」。
3. **影响时间的包含关系**。根因系统的影响窗口通常覆盖或早于下游系统的影响窗口。

## 常见陷阱

**下游先告警，上游后告警。** 典型形态：下游业务成功率告警在前，上游技术告警在后，
但上游日志里的 ERROR 时间最早。此时根因在上游，下游只是表现。

**技术成功率正常但业务成功率暴跌。** 说明本系统自己没报错，是它依赖的某个下游能力不可用，
或者请求发出去了但结果没到达用户。不要因为技术成功率正常就排除这个系统。

**告警文本内部的时间口径矛盾。** 例如窗口写「15:25:00-15:25:50」却说「5min 内出现 510 次」，
两者对不上。遇到这种不要自己挑一个信，写进报告的「材料问题」。
