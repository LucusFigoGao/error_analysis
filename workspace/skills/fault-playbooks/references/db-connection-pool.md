# 数据库连接池故障判读

适用：Druid、HikariCP 等连接池抛出获取连接超时类异常。
典型异常：`GetConnectionTimeoutException`、`CannotGetJdbcConnectionException`、`QueryTimeoutException`。

## 先拿参数

Druid 的异常消息里带一组关键参数，用 `parse_exception` 抽出来：

```
wait millis 3000, active 0, maxActive 30, creating 0, createErrorCount 3054
```

- `active`：当前被业务占用的连接数
- `maxActive`：连接池上限
- `creating`：正在建立中的连接数
- `createErrorCount`：**建连失败的累计次数**

## 判读表

**这是本手册的核心，必须精确匹配，不要跳到常见结论。**

| active | creating | createErrorCount | 故障性质 | 排查方向 |
|---|---|---|---|---|
| 接近 maxActive | 0 | 0 或很小 | **连接池耗尽** | 慢 SQL、连接泄漏、突发流量、事务未提交 |
| **0 或很低** | **0** | **很大且持续增长** | **建连持续失败**，池里根本建不出连接 | **账号密码失效、数据库不可达、数据库侧连接数打满、认证方式变更、证书过期** |
| 0 或很低 | 大于 0 | 0 | **建连挂起**，连接建立过程卡住 | 网络抖动、DNS 解析慢、数据库响应慢、TCP 层问题 |
| 接近 maxActive | 大于 0 | 大于 0 | 混合态 | 先按建连失败查，恢复后再看是否有慢 SQL |

## 最容易犯的错

看到「获取连接超时」就说「连接池不够，建议调大 maxActive、排查慢 SQL」。

**这在 `active=0` 的情况下是完全错误的方向。**

`active=0` 意味着当前没有任何连接被业务占用，池子是空的，不是满的。
配合 `createErrorCount` 很大，说明应用一直在尝试建连、一直失败。
这种情况下调大 maxActive 毫无作用，因为问题不是「上限太低」，而是「一个都建不出来」。

判断口诀：**看 active 不看异常名**。异常名都叫「获取连接超时」，但 active 的值决定了故障性质完全相反。

## createErrorCount 很大意味着什么

这个计数器只在**创建连接失败**时增长，和业务请求量无关。数值达到几千，说明：

1. 失败是持续的，不是偶发抖动
2. 应用在反复重试建连，每次都被拒
3. 故障从开始到现在已经持续了一段时间（按重试间隔可粗估）

持续被拒的常见原因，按生产环境里的出现频率排：

1. **账号密码不对**。数据库侧改了密码，应用配置文件里还是旧的。
   这是最高频的一类，**必须去查最近的改密、用户纳管、权限调整类变更**。
2. 数据库侧连接数打满，新连接被拒
3. 网络策略变更，端口不通
4. 数据库实例异常、主备切换中
5. 认证插件或证书变更

## 接下来做什么

匹配到「建连持续失败」这一行之后：

1. 加载 skill `change-correlation`，重点查改密类变更，时间窗放宽到 7 天
2. 从堆栈里提取出具体的 Mapper、数据源、应用名，用于确认是哪个库哪个账号
3. 把下面这些列进报告的「待验证项」，因为材料里通常拿不到：
   - 数据库侧的登录失败审计日志，确认拒绝原因是认证失败还是别的
   - 应用配置文件里密码的最后修改时间
   - 变更涉及的账号里，哪一个是故障应用在用的
   - 改密后应用是否重启过

## 不要给的建议

- 「调大连接池」：在建连失败场景下无效
- 「增加重试」：会放大对数据库的冲击
- 「重启应用试试」：如果配置文件里还是旧密码，重启之后照样连不上

处置建议必须针对判读表匹配到的那一行给出的排查方向。
