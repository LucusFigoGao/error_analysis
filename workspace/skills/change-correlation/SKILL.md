# 变更关联分析

生产故障里很大一部分由变更引入。材料里只要出现工单号、变更单、发布记录、配置调整，都要按本手册做一次关联判定，不能当背景信息略过。

## 时间窗

- 主窗口：故障前 72 小时
- 改密、证书轮换、权限调整这类变更，窗口放宽到 7 天

理由：这类变更的破坏力有延迟。改密当时连接池里的存量连接还活着，业务正常；等到连接空闲超时被回收、需要重建时才集中爆发，中间可能隔十几个小时甚至几天。**所以「变更在昨天、故障在今天」完全成立，不要因为不是同一时刻就排除。**

## 变更类型到故障模式

| 变更类型 | 典型故障模式 | 特征信号 |
|---|---|---|
| 数据库改密 / 用户纳管 | 应用侧配置未同步，建连失败 | 建连持续失败、createErrorCount 增长、认证类报错 |
| 证书 / 密钥轮换 | 握手失败 | SSL/TLS 异常、握手超时 |
| 应用发布 | 新代码缺陷、依赖不兼容 | 报错集中在新版本节点、回滚后恢复 |
| 配置中心推送 | 参数错误全量生效 | 无发布却突然全量异常、时间点和推送时间吻合 |
| 扩缩容 | 容量不足或连接数超限 | 资源打满、下游连接数超阈值 |
| 网络 / 防火墙策略 | 连不通 | 连接被拒、超时、DNS 解析失败 |
| 数据库参数调整 | 慢查询、锁等待 | 响应时间上升、活跃连接堆积 |

## 改密类变更要重点查什么

这是最容易出事、也最容易被忽略的一类。看到「改密」「纳管」「口令」相关工单，逐条核对：

- **密码存储方式**。写「应用配置文件」的，意味着改密后需要人工改配置 + 重启应用，
  漏做的概率很高。写「密码托管」「自动注入」的风险相对低。
- **人工改密还是自动改密**。人工改密意味着有人工环节，有人工环节就有遗漏。
- **工单状态**。「已解决」「等待确认」不等于应用侧已经同步完成，工单闭环的是数据库侧操作。
- **涉及用户数量**。8 个用户里只要有 1 个是故障应用在用的，就足以引发故障。
  材料里往往不写用户名和应用的对应关系，这一条要列进「待验证项」。
- **是否重启**。改了配置文件不重启，老进程还在用内存里的旧密码。

## 关联强度判定

不要只说「时间接近所以相关」。按下面三条打分：

1. **时序**：变更在故障之前（必要条件，不满足直接排除）
2. **机理**：变更类型对应的故障模式，和实际观察到的症状是否吻合
3. **范围**：变更影响的对象，和故障发生的对象是否重合

三条都满足 → 高置信度
满足时序和机理，范围待确认 → 中置信度，把范围核对写进「待验证项」
只有时序 → 低置信度，只能列为「可能相关的变更」，不能作为根因结论

## 输出要求

关联到的变更要写清楚：工单号、提交时间、变更内容、匹配到的故障模式、置信度、以及还需要核实什么。
